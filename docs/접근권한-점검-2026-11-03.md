# 견적·병원 접근권한 점검

작성일: 2026-11-03

## 확인한 기존 문제와 코드 수정

기존 병원센터는 로그인만 확인했고 브라우저에서 요청 목록을 직접 조회했습니다. 내 견적함은 이메일 입력을 기준으로 조회할 수 있는 구조였습니다. 새 코드는 서버 API에서 인증된 사용자 ID로 자기 요청을 한정하고, 병원센터는 신뢰할 수 있는 app_metadata의 승인 상태를 서버에서 다시 확인합니다. 사용자 편집이 가능한 user_metadata를 권한 판단에 사용하지 않습니다.

- requests: 로그인 사용자 ID와 인증된 이메일로 저장, 지역·카테고리·유한 양수 예산·본문·공유동의 검증
- my-requests: user_id가 로그인 사용자와 같은 요청만 조회
- partner-requests: tangle_approved=true 및 tangle_role=clinic 또는 admin 필요, 목록에 고객 이메일 미포함
- partner-bids: 승인 병원명은 app_metadata.tangle_clinic_name 사용, 병원명·계정 ID 위조 방지, 열린 요청·입력·가격 검증
- callback: 같은 사이트의 상대 경로로만 복귀, 서버/브라우저 모두 SSR 쿠키 인증으로 통일
- 모든 견적 응답 Cache-Control: private, no-store
- 실시간 예약 확정·병원 제휴 인증으로 오해하게 만드는 예시 화면은 상담 준비 안내로 교체

## 운영 DB는 미검증·미변경

이 작업에서 운영 Supabase 인증정보를 읽거나 복사하지 않았고, 고객 요청·제안 데이터를 조회·저장·변경하지 않았습니다. 기존 RLS, 테이블 구조, 뷰, 함수, 트리거가 현재 어떻게 배포돼 있는지는 확인되지 않았습니다.

따라서 견적 연결은 기본 비활성입니다. QUOTE_WORKFLOW_ENABLED=true는 현재 정책 검증 완료라는 운영자의 명시적 설정입니다. 단순 코드 수정이나 화면 차단만으로 운영 DB가 보호됐다고 주장할 수 없습니다. 기존 운영의 직접 DB 접근 문제가 있었다면 운영 정책을 별도로 즉시 점검해야 합니다.

## 활성화 전 필요한 작업

1. 실제 requests·bids의 구조, 기존 정책·뷰·함수·권한, 백업을 확인합니다.
2. supabase/견적접근권한-검토안.sql을 테스트 DB에서 검토합니다. 자동 적용용 마이그레이션이 아니며 아직 실행·SQL 문법 검증하지 않았습니다.
3. requests.user_id, bids.clinic_user_id의 소유권을 검증합니다. 과거 이메일만으로 계정을 자동 연결하지 않습니다.
4. 서버 관리자 경로로만 app_metadata의 tangle_approved, tangle_role, tangle_clinic_name을 지정하고 기존 세션의 토큰 갱신·취소 동작을 확인합니다.
5. 미로그인·일반 회원·요청자·타 사용자·승인 병원·승인 취소 계정으로 직접 REST 접근과 API 접근을 모두 확인합니다.
6. 정책과 스키마를 검증한 뒤에만 QUOTE_WORKFLOW_ENABLED=true를 적용하고 배포합니다.

검토 SQL은 기존의 넓은 permissive 정책을 덮어쓰지 않고 restrictive guard를 함께 적용하는 초안입니다. 적용 대상 정책명이 이미 있으면 트랜잭션이 실패하므로 기존 상태를 확인해야 합니다. 기존 스키마·정책과 충돌 여부, PK 시퀀스 권한, 관련 외부 역할은 실제 DB에서 검토가 필요합니다.
